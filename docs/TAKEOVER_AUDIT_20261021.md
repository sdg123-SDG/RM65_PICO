## 当前代码中的结构性问题

- `real/json_plant.py::RealPlant.canfd` 在 TimeoutError 时返回 SYS_NORMAL。API 返回 0 无法区分应答成功和超时，不能用发送计数作执行验收。
- 同一方法等待首包最多 3 秒，特定 receive_state 响应后又读最多 3 秒的后续包，且忽略第二次读的异常。当前同步调用位于 PICO 控制循环内，理论上一次调用可能占用约 6 秒（另有锁等待）；这与 20 ms 目标周期、250 ms 输入时效、500 ms 反馈时效不相容。最后两帧未出现该长等待，不能将此风险写成已证实的本轮根因。
- `JsonArmLink.rpc` 使用同一 socket 锁串行状态与运动；超时 deadline 在取得锁后才开始，锁等待不计入预算。CANFD 回包仅跳过 current_arm_state，没有像 movej 一样严格匹配命令；后续 recv_json 也没有按消息类型匹配。需用假控制器验证迟到应答、交错状态与无后续包的场景。
- `hold` 在已发送过帧后发当前反馈角 movej。当前失败会中断会话；不得改成吞异常、假成功或盲目重试运动。应先查设备协议与实际回包，再决定退出透传方案。
- `status_suffix` 固定显示 “feedback confirms motion”，无对应的运动确认判定；这是误导性文案。
- 实机与 disconnected preview 的 after_control_tick 取值不同：实机在 commanded/measured 差超过 0.5 度时用 commanded，preview 始终取 measured。现有预览不能完整复现实机输出选择策略。
- 关节 FIFO 仍存在。同步发送限制了源推进速度，但遇到反馈窗口限流时队列仍可能增长；不能宣称已从结构上消除积压。
